// App.tsx:25-27 — the ONLY place state changes:
function deleteHabit(id: string) {
  setHabits((prev) => prev.filter((h) => h.id !== id));
}

2 What filter() does inside

Say state is 3 habits and you delete id-2. Filter builds a new array, keeping only items where h.id !== id is true:

itemcheck h.id !== "id-2"result
☕ Drink water (id-1)"id-1" !== "id-2" → trueKEEP ✅
📖 Read (id-2)"id-2" !== "id-2" → falseDROP ❌
🏃 Run (id-3)"id-3" !== "id-2" → trueKEEP ✅

New array = [id-1, id-3]. Old array is never mutated — React needs a new reference to know it must re-render. That's why we use filter and not splice.

3 Re-render + why key matters

// HabitListe.tsx:25-29
{habits.map((habit) => (
  <li key={habit.id}>   // ← stable identity
    <HabitItem habit={habit} onDelete={onDelete} />
  </li>
))}

After setHabits(newArray): React re-runs App → HabitList with 2 items instead of 3. Because each <li> has key={habit.id}, React knows exactly which DOM node belonged to id-2 and removes only that one. Without a stable key (e.g. using index), the wrong row could disappear.

4 The closure trap (most common bug)

// ✅ CORRECT — arrow function: runs ONLY when clicked
<span onClick={() => onDelete(habit.id)}>Delete</span>

// ❌ WRONG — calls during render: deletes everything instantly / infinite loop
<span onClick={onDelete(habit.id)}>Delete</span>

Each row's () => onDelete(habit.id) is a closure: it remembers that row's own habit.id. That's how the generic deleteHabit(id) in App knows which one you clicked.

5 Full loop + localStorage

// App.tsx:17-19 — after every habits change, persist:
useEffect(() => {
  localStorage.setItem("habits", JSON.stringify(habits));
}, [habits]);

Click → onDelete(id) → filter → setHabits → re-render (one <li> gone) → useEffect saves new array to localStorage. Refresh-proof.
